# Laravel 搬移至 AWS Aurora DSQL 實戰與踩坑筆記

## 前言與架構背景

原本在 AWS Lambda 上運行 Laravel（透過 Bref）若使用 **SQLite on EFS**，雖然省下了 RDS 的費用，但 Lambda 為了掛載 `/mnt/efs` 必須被綁進 VPC 私有子網，連帶需要 NAT Gateway（否則無法對外呼叫 S3、Turnstile、Twitter oEmbed 等外部服務），且同時多台 Lambda 寫入同一個 SQLite 檔案時會有檔案鎖瓶頸。

將資料庫搬移至 **Amazon Aurora DSQL**（基礎觀念可先參考 [Amazon Aurora DSQL 介紹](/aws/aurora-dsql)）後，整個架構可以大幅簡化：

- **移除 VPC 與 EFS**：Lambda 直接走 Aurora DSQL 公開端點 + IAM Token 驗證，不需掛載 `/mnt/efs` 與 NAT Gateway。
- **其餘無伺服器配套**：Cache 改用 `dynamodb`、Queue 改用 `sqs`、靜態資產與檔案上傳走 S3、Log 輸出至 `stderr`。
- **Web Runtime**：使用 Bref 的 Laravel Octane Handler（`OCTANE_PERSIST_DATABASE_SESSIONS=1`）減少重複握手與簽章延遲。

不過，**Aurora DSQL 並不是「改個 `.env` 的 `DB_CONNECTION` 就能無痛切換」的傳統 PostgreSQL**。這篇筆記記錄實際將一個運行多年的 Laravel 專案從 SQLite 搬移到 Aurora DSQL 時，真正改動到的地方與必須避開的坑。

---

## 一、安裝與基礎設定：`bref/laravel-dsql`

Bref 官方維護了 [`bref/laravel-dsql`](https://github.com/brefphp/laravel-dsql) 套件，用來提供 Laravel 的 `dsql` 資料庫驅動（支援 Laravel 12 與 13）：

```bash
composer require bref/laravel-dsql
```

### 1. 檢查 `composer.json` 的 AWS SDK 裁剪清單

許多 Bref / Lambda 專案為了縮小打包體積，會在 `composer.json` 中設定 `extra.aws/aws-sdk-php` 來移除未使用的 AWS SDK 服務。

如果專案有設定這個白名單，**務必加上 `"DSQL"`**：

```json
{
    "extra": {
        "aws/aws-sdk-php": ["S3", "Sqs", "DynamoDb", "DSQL"]
    }
}
```

若沒保留 `"DSQL"`，`DsqlServiceProvider` 在建立連線時會因找不到 `Aws\DSQL\AuthTokenGenerator` 而直接拋出 `LogicException`。如果原本就沒有設定 `extra.aws/aws-sdk-php`，則完整 SDK 預設都存在，不需額外新增該區塊。

### 2. `config/database.php` 與本機/測試環境共存

`bref/laravel-dsql` 的 `DsqlServiceProvider` 會自動透過 `mergeConfigFrom()` 幫 `config/database.php` 註冊好一個 `dsql` 連線，內容等同於：

```php
'dsql' => [
    'driver' => 'dsql',
    'host' => env('DB_HOST'),
    'port' => '5432',
    'database' => 'postgres',
    'username' => env('DB_USERNAME', 'admin'),
    'charset' => 'utf8',
    'prefix' => '',
    'prefix_indexes' => true,
    'search_path' => 'public',
    'sslmode' => 'verify-full',
    'sslrootcert' => env('DB_SSLROOTCERT', 'system'),
],
```

因此：

- **不需要手動複製整個 `'dsql'` 區塊進 `config/database.php`**（避免重複維護，套件預設已將 `sslmode` 設為 `verify-full` 並讀取 `DB_SSLROOTCERT`）。
- **`default` 維持 `env('DB_CONNECTION', 'sqlite')`**：正式環境由 Terraform 注入 `DB_CONNECTION=dsql`、`DB_HOST`、`DB_PORT=5432`、`DB_DATABASE=postgres`、`DB_USERNAME=admin`（無需 `DB_PASSWORD`）；本機開發（`.env` 為 `sqlite`）與自動化測試（`phpunit.xml` 使用 `sqlite` + `:memory:`）完全不受破壞。

### 3. 套件已經幫我們處理好哪些事？

先理解 `bref/laravel-dsql` 已經解決了什麼，才能知道哪些坑需要**應用程式自己處理**：

- **IAM Token 簽發**：每次呼叫 `DsqlConnector::connect()` 都會用環境中的 AWS Credentials 本地簽發新的 IAM Auth Token（`admin` 用 `dsql:DbConnectAdmin`，其他角色用 `dsql:DbConnect`）。
- **OCC 衝突自動重試（`SQLSTATE 40001`）**：單一 SQL 敘述失敗時會隨機退避並重試最多 3 次；同時擴充了 `DsqlCacheStore` 與 `DsqlBatchRepository` 的原子計數重試。
- **關閉 Savepoints 與 Migration Transaction**：`DsqlQueryGrammar::supportsSavepoints()` 回傳 `false`，`DsqlSchemaGrammar::$transactions = false`（確保每條 DDL 獨立執行）。
- **自動轉換 `id()` 與索引語法**：自動將自增主鍵編譯為 `bigint generated by default as identity (cache 1)`，將索引編譯為 `create index async` / `create unique index async`，並在 `UPDATE/DELETE ... JOIN/LIMIT` 時以 `id` 取代 PostgreSQL 的 `ctid`。

## 二、搬移過程最重要的 6 大注意事項與踩坑解析

### 注意事項 1：歷史 Migrations 幾乎一定會撞上 DSQL DDL 限制（最容易爆炸！）

即使專案以前在 MySQL、PostgreSQL 或 SQLite 都能順利跑完 `php artisan migrate`，**只要是經營一段時間的舊專案，累積下來的歷史 `ALTER TABLE` migration 在全新 Aurora DSQL 上高機率會直接失敗**。

`DsqlSchemaGrammar` 在編譯階段就會直接嚴格檢查並拋出 `LogicException`，實戰上最常見的 6 個雷區如下：

#### 雷區 1：對既有資料表 `ADD COLUMN` 加上 `NOT NULL` 或 `DEFAULT`

```php
// ❌ DSQL 會失敗：DsqlSchemaGrammar::compileAdd() 直接拋出 LogicException
Schema::table('posts', function (Blueprint $table) {
    $table->boolean('is_private')->default(false)->after('body');
});
```

Aurora DSQL 規定對既有表新增欄位**必須是 `nullable()` 且不能有 `default` 值**（如果要加預設值，必須拆成兩步：先加 `nullable()` 無預設值欄位，再另外 `change()` 加上 `default()`，且舊資料列仍會保留 `NULL`）。

#### 雷區 2：使用 `->change()` 修改欄位型別或設為 `NOT NULL`

```php
// ❌ DSQL 會失敗：compileChange() 要求必須維持 nullable()，且不會變更欄位型別
Schema::table('categories', function (Blueprint $table) {
    $table->text('icon')->change();
});

// ❌ DSQL 會失敗：不能將既有欄位改為 NOT NULL
Schema::table('passkeys', function (Blueprint $table) {
    $table->string('owner_type')->nullable(false)->change();
});
```

#### 雷區 3：在同一個 Migration 混用 DDL 與 DML

```php
// ❌ 容易在 DSQL 踩雷：建表/改表後立刻 DB::table()->update(...)
Schema::table('passkeys', function (Blueprint $table) {
    $table->string('owner_type')->nullable();
});

DB::table('passkeys')->update(['owner_type' => 'App\Models\User']);
```

Aurora DSQL 不允許在同一交易內混用 DDL 與 DML；即使是拆開執行，後續也無法再把 `owner_type` 改回 `NOT NULL`。

#### 雷區 4：舊版 `json()` 欄位與 `renameIndex()`

- 若資料表只是儲存序列化 JSON、**沒有用到資料庫層的 JSON 查詢或索引**（例如 `settings.value`、`passkeys.data`），建議將 migration 欄位改為 `text()`，Model 上的 Eloquent cast（`'json'` 或 `'array'`）完全照舊保留即可，跨 SQLite / PostgreSQL / DSQL 最穩妥。
- 歷史上曾對欄位或索引改名（例如 `renameColumn` 搭配後續的 `renameIndex()` 產生 `alter index ... rename to ...`），在全新資料庫建表時其實完全是多餘的步驟。

#### 雷區 5：`down()` 中使用 `truncate()`

```php
// ❌ Aurora DSQL 不支援 TRUNCATE
DB::table('categories')->truncate();

// ✅ 改用 DELETE
DB::table('categories')->delete();
```

#### 實戰解法：整併為乾淨的 Baseline Migrations

如果這顆 Aurora DSQL 是**全新空白的目標資料庫**，最乾淨的做法不是硬寫一堆繞過 DDL 的補丁，而是**把歷年針對同一張表「新增欄位、改名欄位、改欄位型別、刪除欄位」的歷史 migration 全部收斂回原本的 `create_*_table` 與初始 seed migration 中**，並刪除冗餘的歷史 `alter` migration 檔案：

- 建表當下就擁有最終正確的欄位型別（例如 `categories.icon` 直接是 `text()->nullable()`、`posts` 直接包含 `is_private` 與 `cover_image_url` 與 `softDeletes()`、`passkeys` 直接使用 `$table->morphs('owner')`）。
- 讓所有 `PRIMARY KEY`、`UNIQUE`、`FOREIGN KEY` 都能在 `CREATE TABLE` 內一次宣告完成。
- 讓 `php artisan migrate --force` 在全新 DSQL 資料庫上一次順利通過，且最終 Schema 與原本完全一致。

> [!WARNING]
> 整併歷史 migration 檔名後，**本機開發環境若有舊的 `database/database.sqlite`**，其 `migrations` 資料表裡還記錄著被刪除的舊檔名，需執行 `php artisan migrate:fresh`（如有需要保留的測試資料請先備份）重新對齊本機 `migrations` 紀錄。

#### 進階驗證技巧：不連真機也能用測試驗證全部 Migrations

在 CI 或本機尚未連上真實 DSQL Cluster 時，可以利用 `DsqlConnection` 搭配 Laravel 的 `pretend()` 模式，把所有 migration 的 `up()` 與 `down()` 跑過一遍 `DsqlSchemaGrammar`，提前在單元/整合測試中攔截所有不相容語法：

```php
test('all migrations compile cleanly through DsqlSchemaGrammar without unsupported DDL', function () {
    $dsqlConnection = new DsqlConnection(
        new PDO('sqlite::memory:'),
        'postgres',
        '',
        [
            'driver'         => 'dsql',
            'name'           => 'dsql_pretend',
            'database'       => 'postgres',
            'prefix'         => '',
            'prefix_indexes' => true,
            'search_path'    => 'public',
        ],
    );

    config(['database.connections.dsql_pretend' => ['driver' => 'dsql_pretend']]);
    DB::extend('dsql_pretend', fn () => $dsqlConnection);

    $originalDefault = DB::getDefaultConnection();
    $migrationFiles = glob(database_path('migrations/*.php'));
    sort($migrationFiles);

    try {
        DB::setDefaultConnection('dsql_pretend');

        $queries = $dsqlConnection->pretend(function () use ($migrationFiles): void {
            foreach ($migrationFiles as $file) {
                $migration = require $file;
                $migration->up();
                $migration->down();
            }
        });
    } finally {
        DB::setDefaultConnection($originalDefault);
        DB::purge('dsql_pretend');
    }

    $sqlStatements = array_column($queries, 'query');
    $combinedSql = strtolower(implode("\n", $sqlStatements));
    $ddlSql = strtolower(implode("\n", array_filter(
        $sqlStatements,
        fn (string $sql): bool => str_starts_with(strtolower($sql), 'create ')
            || str_starts_with(strtolower($sql), 'alter ')
            || str_starts_with(strtolower($sql), 'drop '),
    )));

    expect($combinedSql)->not->toContain('truncate ');
    expect($ddlSql)->not->toMatch('/\bjsonb?\b/');
    expect($ddlSql)->not->toContain('alter index ');
    expect($ddlSql)->toContain('generated by default as identity (cache 1)');
    expect($ddlSql)->toContain('create index async ');
});
```

> [!TIP]
> 注意測試斷言時要將 DDL（`create`/`alter`/`drop`）與 DML（`insert`）分開檢查！如果剛好有 seed 資料內容包含 `"JSON"` 字串（例如技術標籤 `['name' => 'JSON']`），直接對整份 SQL 做 regex 檢查會誤報。

### 注意事項 2：SQLite → PostgreSQL / DSQL 查詢語法差異

從 SQLite 切換到 PostgreSQL/DSQL 時，語法上最容易忽略卻會在執行期才爆開的差異如下：

#### 1. `LIKE` 的大小寫敏感差異

- **SQLite** 的 `LIKE` 預設**不區分大小寫**。
- **PostgreSQL / Aurora DSQL** 的 `LIKE` **嚴格區分大小寫**！如果搜尋框或 Artisan 指令寫 `where('name', 'like', "%{$value}%")`，輸入小寫 `laravel` 將找不到 `Laravel`。
- **正確寫法**：改用 Laravel 內建的 `whereLike()` / `orWhereLike()`（`caseSensitive` 預設為 `false`），在 PostgreSQL / DSQL 會自動編譯為 `ILIKE`，在 SQLite 則維持 `LIKE`：

```php
// ❌ SQLite 不分大小寫，但在 DSQL 會區分大小寫
Tag::where('name', 'like', "%{$value}%");

// ✅ DSQL 自動編譯為 ILIKE，SQLite 維持 LIKE
Tag::whereLike('name', "%{$value}%");

Link::whereLike('title', "%{$value}%")
    ->orWhereLike('url', "%{$value}%");
```

#### 2. Boolean 型別嚴格比對

- SQLite 內部以 `0` / `1` 儲存布林值，因此 `where('is_private', 0)` 在 SQLite 能跑，但**在 PostgreSQL / DSQL 會直接報型別錯誤**（`boolean = integer` 不相容）。
- 務必在所有 Eloquent 查詢與 Migration 寫入中使用 PHP 原生 `true` / `false`（例如 `->where('is_private', false)`），並在 Model 設定 `casts()` 為 `'boolean'`。

#### 3. 全面清查 SQLite 專屬語法與 DSQL 不支援 SQL

搬移前建議在 `app/`、`database/`、`routes/`、`resources/` 全面搜尋並排除以下項目：

- **SQLite 專屬語法**：`PRAGMA`、`strftime`、`GROUP_CONCAT`、`IFNULL`、反引號 `` ` ``
- **JSON SQL 查詢**：`whereJsonContains`、`whereJsonLength`、`->`、`->>`
- **不支援物件/操作**：`truncate()`、Triggers、Stored Procedures、Temp Tables
- **自寫 Raw SQL**：例如 `WITH RECURSIVE` 遞迴 CTE（如果專案中有留下未實際使用的 CTE 存取器，建議標記盤點並在真正啟用前於 DSQL 實機驗證或改寫為應用層查詢）。

### 注意事項 3：Bref Octane 長連線與 DSQL 1 小時上限

在 AWS Lambda 上為了降低每次請求的 TLS 握手與 IAM 簽章延遲（並避免觸及 DSQL 每秒新連線數限制），Bref 建議搭配 Laravel Octane 並設定：

```text
OCTANE_PERSIST_DATABASE_SESSIONS=1
BREF_LOOP_MAX=250
```

這個設定會讓 `Bref\LaravelBridge\Octane\OctaneClient` 在每個 HTTP 請求結束後**不呼叫 `$connection->disconnect()`**，讓 PDO 連線留在 Lambda 記憶體中重複使用，並在累積處理達 `BREF_LOOP_MAX` 次請求後重啟 Worker 回收資源。

同時需留意 Aurora DSQL 單一連線的最長存活上限為 **60 分鐘（1 小時）**，超過時間後服務端會主動中斷連線。當架構上有長駐 Worker（或低流量容器長時間維持暖機）時，建議搭配 `BREF_LOOP_MAX` 並觀察 CloudWatch Logs 是否出現連線逾時斷開的情況。

### 注意事項 4：清除 EFS / SQLite 殘留路徑與驗證 CI 無資料庫打包

1. **搜尋專案殘留路徑**：全面掃描 `/mnt/efs` 與寫死的 `database.sqlite` 路徑，確認 Production 的 Artisan Command、檔案上傳、Log、Cache、Session 都不會嘗試讀寫已移除的 EFS 目錄。
2. **確認 CI Pre-build 指令不依賴資料庫連線**：在 GitHub Actions 打包產物時還連不到 Aurora DSQL，建議於本機以假 DSQL 環境變數模擬 CI 打包階段的指令（例如 `config:clear`、`feed:install`），確認不會嘗試建立資料庫連線：

```bash
DB_CONNECTION=dsql \
DB_HOST=<cluster-id>.dsql.<region>.on.aws \
php artisan config:clear && \
DB_CONNECTION=dsql \
DB_HOST=<cluster-id>.dsql.<region>.on.aws \
php artisan feed:install --no-interaction
```

### 注意事項 5：SSM Parameter Store 與環境變數衝突檢查

當 Terraform 已經直接把 DSQL 變數注入 Lambda Environment Variables 時，如果專案同時使用 AWS SSM Parameter Store（例如 `/docfunc/env`）載入環境變數，**務必檢查兩者不能互相衝突或覆蓋**：

- **應從 SSM 移除的舊變數**：
    - `DB_CONNECTION`、`DB_HOST`、`DB_PORT`、`DB_DATABASE`、`DB_USERNAME`（避免舊的 SQLite/MySQL 值覆蓋 Terraform 注入的 DSQL 連線資訊）
    - `DB_PASSWORD`（DSQL 改用 IAM Token 驗證，不應殘留靜態密碼）
    - `DB_URL`、`DB_FOREIGN_KEYS`、`DB_SOCKET` 等舊設定
    - 任何指向 `/mnt/efs` 的路徑設定
- **應確認無誤的配套變數**：
    - `CACHE_STORE=dynamodb`
    - `QUEUE_CONNECTION=sqs`
    - `QUEUE_FAILED_DRIVER=database-uuids`（或 `dynamodb`）
    - `SESSION_DRIVER=database`（或 `dynamodb` / `cookie`）
    - `LOG_CHANNEL=stderr`
    - `OCTANE_PERSIST_DATABASE_SESSIONS=1` 與 `BREF_LOOP_MAX=250`

### 注意事項 6：部署後執行 `migrate --force` 與資料搬移細節

1. **在全新空白 DSQL Cluster 執行 `php artisan migrate --force`**：若測試用的 Cluster 曾經跑過失敗的舊 migration，建議先清空 schema 後再重跑，確保 `migrations` 表狀態乾淨。
2. **非同步索引建立時間**：DSQL 使用 `CREATE INDEX ASYNC`，雖然 `migrate --force` 返回成功，但索引是在背景建立，剛建表後幾秒內大量查詢需留意索引建置進度。
3. **若有從舊 SQLite 匯入既有資料的需求**：
    - Seed migration 已寫入的初始資料（如預設分類、連結、標籤、預設設定）勿重複插入。
    - 若匯入時保留原本的 `id`，匯入後必須對每張表重設 PostgreSQL identity sequence，否則之後新增資料會發生主鍵衝突：
        ```sql
        SELECT setval(pg_get_serial_sequence('posts', 'id'), COALESCE(MAX(id), 1)) FROM posts;
        ```
    - SQLite 的 `0` / `1` 布林欄位須明確轉成 `false` / `true`。
    - 單筆寫入交易需分批（Batch），避免觸及 Aurora DSQL 單次交易最多 **3,000 列** 或 **10 MiB** 的限制。

## 三、搬移前後快速檢核清單

- [ ] 安裝 `bref/laravel-dsql`（確認 `composer.json` 若有 `extra.aws/aws-sdk-php` 已包含 `"DSQL"`）
- [ ] 確認 `config/database.php` 與 `phpunit.xml` 不影響本機 SQLite 開發與自動化測試
- [ ] 盤點並整併所有不相容 DSQL 的歷史 `ALTER TABLE` / `truncate()` / `json()` migrations
- [ ] 撰寫 `DsqlConnection::pretend()` 測試，確認全部 migrations 編譯零 `LogicException`
- [ ] 將 `LIKE` 查詢改為 `whereLike()` / `orWhereLike()`，並全面清查 boolean 比對、SQLite 語法與 Raw SQL
- [ ] 設定 Octane `OCTANE_PERSIST_DATABASE_SESSIONS=1` 與 `BREF_LOOP_MAX=250`
- [ ] 搜尋並移除所有 `/mnt/efs` 與寫死的 `database.sqlite` 路徑
- [ ] 在未連 DB 環境驗證 CI 打包 Artisan 指令可正常完成
- [ ] 清理 SSM Parameter Store 舊資料庫/EFS 環境變數，部署後執行 `php artisan migrate --force`
